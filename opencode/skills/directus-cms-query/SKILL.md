# Trace Sports Platform CMS Directus Queries

Use this workflow especially when the user provides a URL. Treat that URL as the starting input and trace its request through the application to the code that builds the Directus query. Do not jump straight from a URL slug to a guessed collection or MCP lookup.

## Establish the target

1. Preserve the supplied URL exactly, then parse scheme/host, brand, path segments, and query string. Use the host to identify the brand when possible; use the path and query string as route inputs. Common brands include `covers`, `apuestasdeportivas`, `betca`, `sportsbookreview`, and `sportsillustrated`.
2. Establish whether the URL represents the ASP.NET Web app, Commercial API, or another service, and identify its environment from the hostname/configuration. Do not assume the local default brand or environment when the URL specifies them.
3. If the host is not enough to establish brand or environment, inspect project config and state the unresolved assumption; ask only if it blocks a meaningful trace.
4. Read `AGENTS.md`, the applicable `.github/instructions/*.instructions.md`, and project-local setup guidance before suggesting or making code changes. Follow repository guidance, including the restriction against adding `SiteId` branches in shared application logic or Razor views.

## Trace the application request before querying Directus

For a supplied URL, follow the actual HTTP request path in order. Use code searches and routing/configuration, not assumptions based only on route naming:

1. Match the hostname and path/method to the application's host setup, ASP.NET route attributes/conventions, controller/action or endpoint, and any route rewrite/proxy behavior. For web page URLs, establish what server-side request handles that page; don't mistake client-side links, frontend API calls, or a similarly named page for the route's CMS request.
2. Substitute the supplied path and query parameters into the route values and follow the action/endpoint into its view model, MediatR request, service, or API client. Continue through each request/handler until reaching the CMS client call(s). A route can make multiple CMS requests; report all relevant branches and their triggering conditions.
3. Identify the Directus collection for each call (often `[DirectusCollection("...")]` or a literal passed to `new CmsQuery(...)`).
4. Reconstruct the **effective request for this URL**, not just a generic query template: resolve values sourced from route/query parameters, defaults, configuration, and conditional branches. Record HTTP method/path plus collection and every query parameter: `filter`, `deep`, `fields`, `sort`, `limit`, `offset`/`page`, `meta`, and single-item behavior. Inspect the query builder and HTTP client serialization code (including `CmsQuery.Build()` or equivalent) to establish how parameters are encoded and which defaults are emitted.
5. Give the user the **exact Directus request generated by the supplied URL** as a copyable code block: HTTP method and full request URL, including the Directus `/items/<collection>` path and the complete serialized query string with actual values and encoding. Do not substitute an abstract parameter list for this request when the code path permits reconstructing it. If any values genuinely depend on runtime context, provide the exact known request plus clearly labeled unresolved placeholders, and show the concrete conditional request variants. If a route triggers multiple Directus calls, give a separate exact request for each call and identify its trigger. Never invent omitted defaults or pretend unspecified runtime values are known; explain precisely why the request cannot be fully resolved when necessary.
6. If the URL lacks a content identifier or requires request context (geo, locale, headers, cookies, current time, feature flags), trace those inputs and show which query clauses or requests depend on them. Do not invent missing values; present conditional query variants when needed.
7. When a query is built via `CmsQueryFactory.FromDto<T>()`, inspect the DTO and `CmsQueryFactory.GenerateFieldsFromType`; do not assume generated `Fields` are just scalar DTO properties. Enumerate its wildcard and expanded relationship paths for the actual DTO used by this call.
8. Follow configuration loading to establish the brand and environment settings. Check `WHITELABEL_SITE_ID`, the relevant `appsettings.<environment>.<brand>.json`, and local override existence where relevant. Never print or repeat Directus tokens or other secrets from local configuration.

Do not query Directus or conclude what record is read until the source-code trace establishes the collection and effective filters. If source tracing cannot resolve a call, name the exact missing link and show the closest verified evidence instead of guessing.

Separate **what the application code requests** from **what the MCP returns**. Note where CMS instance, environment, permissions, or current data may differ. Do not claim a live MCP result proves the app's exact runtime response if those differ.

## Never use test fixtures as content evidence

- Do not use test fixtures, snapshots, mocked CMS responses, captured API responses, or test data to answer questions about what content currently exists in Directus or what a URL currently displays.
- This explicitly includes files under `**/Fixtures/**`, fixture JSON, `Cms.Testing` fixture repositories, mocked `ICmsClient` implementations, and test setup/configuration. Do not quote, summarize, or infer real CMS content from them, even if they appear to match the URL or brand.
- Fixtures and tests may be inspected only to understand code mechanics (for example, how a request is constructed or a query is asserted), and must never be treated as evidence of live content or used in the content answer.
- For content facts, use a correctly mapped live Directus MCP read and clearly identify the instance/environment. If no matching live instance is available, say that current content could not be verified; report only the code-derived query and do not fill in content from fixtures.
- Whenever a live Directus read identifies the exact item(s), include a clickable link to each item in that Directus instance's admin UI. Build the link from the verified instance base URL, collection name, and the exact primary-key value returned by the live read (normally `https://<directus-host>/admin/content/<collection>/<primary-key>`); URL-encode path segments as needed. Never construct an item link from a fixture, an inferred/guessed ID, or an unverified MCP-to-brand mapping. If the item is known from code but no live item read established its ID, or the deployment's admin route cannot be established, state that a reliable item link is unavailable rather than fabricate one.

## Choose the Directus MCP

The global OpenCode config has these Directus MCPs. They are intended to represent the following production targets, but **verify the effective endpoint before choosing a server**:

| Brand / instance | MCP name |
| --- | --- |
| `apuestasdeportivas` / Adcom | `directus_adcom_prod` |
| `betca` | `directus_betca_prod` |
| `sportsbookreview` / SBR | `directus_sbr_prod` |
| `sportsillustrated` / SI | `directus_si_prod` |
| Covers CMSP | `directus_covers_cmsp_prod` |
| Covers legacy | `directus_covers_legacy` |

Do not infer the target from the MCP name alone. Inspect the resolved OpenCode MCP config when needed (for example, `opencode debug config`) and compare `DIRECTUS_URL` with the app's selected environment `Cms:BaseUrl` / `Cms:ReadOnlyBaseUrl`; do not expose or repeat `DIRECTUS_TOKEN` or config secrets. At the time this skill was authored, the resolved `directus_adcom_prod` and `directus_betca_prod` URLs both showed the Covers CMSP production host despite their names. Until those environment-variable values are checked/fixed, do not treat either MCP as Adcom or Betca data. For `covers`, distinguish CMSP versus legacy by endpoint and app configuration, not brand name. If the app points at a dev/UAT endpoint but only a prod MCP is available, state that the MCP result is a production comparison, not the same instance.

## Inspect live data carefully

- Use only the matching Directus MCP's schema/collection/item **read** tools to inspect data. Check the collection and fields before making a targeted item query.
- Translate the code's effective filter into the MCP read filter as faithfully as its query format allows. Report any syntax/semantics that could not be represented exactly (including relation filters, nested `deep` filters, URL encoding, or pagination differences).
- Use the code's identifiers (slug, id, URL path, tag IDs/slugs, status) as the basis of the read. Avoid broad collection dumps when a narrow query is possible.
- MCP permissions may allow writes, but this investigation is read-only: never create, update, delete, import, or trigger a Directus flow unless the user separately and explicitly requests that mutation.
- Distinguish missing/permission-filtered MCP results from proof that the app cannot read the record. Mention relevant filters, published status, permissions, and environment when interpreting empty results.

## Present the result

Summarize:

- brand, environment, app/route, and which instance was inspected;
- original URL and matched route/controller/action or endpoint;
- code path (routing → request/handler/service → CMS client call → collection/query);
- exact, copyable Directus HTTP method and full request URL, including its complete serialized query string for every call triggered by the URL; use actual values/encoding and clearly label only genuinely unresolved runtime values or conditional variants;
- key fields and expanded relations;
- a concise description of matching live data, if retrieved, with a clickable Directus admin link for every exact item returned;
- instance/environment or query-equivalence caveats.

Include file paths and line numbers for the code trace. Be precise about facts from code versus facts observed through the MCP.
